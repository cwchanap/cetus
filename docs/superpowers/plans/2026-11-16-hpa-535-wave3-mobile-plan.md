# HPA-535 — Port seven wave-3 games to Expo: single-PR implementation plan

**Status:** Revised after [first design review](https://github.com/cwchanap/cetus/pull/110#pullrequestreview-5941818871) and [follow-up integration review](https://github.com/cwchanap/cetus/pull/110#pullrequestreview-5942665486), 2026-11-17. Still docs-only: all implementation and verification boxes are unchecked.
**Linear:** [HPA-535](https://linear.app/cwchanap/issue/HPA-535/port-the-wave-3-games-to-mobile-7-heavy-canvas-games) · **Design:** [Wave-3 design](../specs/2026-11-16-hpa-535-wave3-mobile-design.md)
**Base:** current `main` after [HPA-533 / PR #108](https://github.com/cwchanap/cetus/pull/108); mobile **16/23** playable.
**Delivery:** **One PR for HPA-535.** This draft starts with the two docs; all stages below become *commits within this same PR*. No per-game PRs. Keep the existing `NATIVE_GAMES`, `NativeGameHost`, `NativeGameChrome`, `GameCanvas`, `useGameLoop`, `createHandleSession`, `@cetus/api-client` and `@cetus/games`. Add only a normalized runtime producer, a small shared frame-loop core, and one pure Ice Slide score policy. No generic plugin framework.
**Separate asset task:** [HPA-1140](https://linear.app/cwchanap/issue/HPA-1140/create-an-original-60-second-rhythm-reactor-metronome-audio-asset) delivers original rhythm audio independently; no music, image or SFX creation in the code PR. **Decision: do not merge this PR at 22/23**. If HPA-1140 is not ready, leave this **one** PR in draft and wait for the asset before completing Rhythm.
**Release follow-on:** [HPA-199](https://linear.app/cwchanap/issue/HPA-199/verify-cross-platform-parity-and-release-on-the-app-store-and-google) owns **real cross-platform authenticated** parity, Android native/device verification and store release.

## Stage 1 — Circuit Hacker **with** the minimal native handle seam (16 → 17)

- [ ] Preserve **`NativeGameEntry.port?: NativeGamePort` and all 16 existing entries/test fixtures**; add a distinct typed `handlePort` variant. Introduce **two explicit native runtime producers** yielding one common `{ session, binding, view, outcomeLabel?, onRewards, onRunStart, dispose }`. BaseGame maps the existing `port.resultOutcomeLabel(result.stats)` to the runtime's `(result: GameSessionResult) => string | null`; handle games can label Solved/Time's up/other local results. Keep `port.view`/per-instance `game` board prop for existing BaseGame Jest bindings. `NativeGameHost` creates **one** identity-bound `createScoreSubmitter(settledUserId)`, consumes the normalized runtime and keeps one `useGameSession` + `NativeGameChrome` (no scattered branches). Retain **`forwardBaseGameResults` → `createBaseGameSession`** usage in the BaseGame producer and its tested cleanup order **forwarder removed → session disposed → model destroyed**, without rewriting the existing host mocks and tests.
- [ ] Extract the existing reward banner's merge reducer once, reused for both producers. Keep the BaseGame rule: stale prior-run result never overwrites current UI; **late same-account rewards are still delivered** if the old score committed. Runtime disposal/account switch suppresses further UI updates, and the model cleanup remains idempotent.
- [ ] Write **one** handle-result helper for all three handle titles, reusing `createRunGuard`. `beginRun` resets visible **score and time**, then score-eligible finish publishes pending, issues **one** injected score POST with `platform`, `gameData`, `context`, then saved/unconfirmed; forward awards once even for late same-account saves, but never overwrite the new run's result. For non-save finish, omit `saveStatus` entirely. No retries/duplicates. **Fix `packages/app-core/src/createHandleSession.ts` so `onStart` and `onIdle` also clear `result: null`**; existing web islands still work. Update the `GameSessionResult.saveStatus` doc in `packages/app-core/src/types.ts` to clarify optional saved-state reporting: handle eligible saves now use pending/saved/unconfirmed; no-save outcomes omit it. Keep `pausable:false` for models with no pause API and existing AppState capability gating.
- [ ] Add **real first consumer**: `CircuitHackerBoard.tsx` using Skia, pre-run difficulty, lazy grid generation on Start, tap-to-`rotateTile`, powered/locked tiles and model-owned timeout. **There is no `CircuitHackerGame.setDifficulty()`**: a thin per-host controller stores difficulty, constructs/replaces `CircuitHackerGame({difficulty,cellSize}, callbacks)` **before** zero-argument `actions.start()` (cleaning up previous instance), then calls `startGame()`; Replay uses the selected difficulty. The controller is the board `binding`, not an assumed raw model prop. Bind `onGameStart/onTimeUpdate/onRotation/onSolved/onFail`; solve posts once with `{difficulty,secondsRemaining,rotationsUsed,solved}`, timeout/manual failure does **not** POST.
- [ ] Register `GameID.CIRCUIT_HACKER`; update `NativeGamesRegistry.test.ts` and `GamesHub.test.tsx` IDs/counts **in this registration commit** (**16→17**, six disabled); extend `NativeGameImportGraph.test.ts` for the new producer without DOM/Pixi imports.
- [ ] Jest and app-core Vitest: shared-host regression across both variants, **legacy `NativeGameHost.test.tsx` mocked calls and exact teardown order**, outcome labels, controller's pre-run difficulty selection and Replay, lazy grid generation/locked tile, one POST on solve/no POST on fail, pending/saved/unconfirmed, **`onStart`/`onIdle` clearing an old result**, new-run score/time reset, guest/platform binding, account-switch cleanup, stale result discarded **while same-account late rewards still forward**, no fabricated Pause. **MCP iOS simulator**: select difficulty → Start → rotate tiles → solve/fail → result → Replay/back; screenshot active/solved/failed states.

**Checkpoint:** one common host backed by two real producers, Circuit playable (**17/23**). No unused handle abstraction stage and no second native chrome.

## Stage 2 — Satellite Sync and shared frame-loop core (17 → 18)

- [ ] Extract the rAF scheduling, wake subscription, capped delta, idle timestamp reset, lifecycle `onFrame` and cleanup from `useGameLoop` into a **small** `useFrameLoop({isRunning,step,subscribe,onFrame,lifecycleKey})` core. Keep existing `useGameLoop(game,onFrame)` as a BaseGame adapter with identical behavior and no changes to the 16 existing boards. Add Jest proving Start/Reset/Pause lifecycle rendering, first-delta zero, 0.1s wall-delta cap, one loop, unmount cancellation and callback freshness.
- [ ] Create `SatelliteSyncBoard.tsx`: Skia orbital rings, moving targets/obstacles and beams; pan `beginAim/updateAim/endAim` using portable geometry helpers; no duplicate orbital math. Subscribe to controller lifecycle callbacks to wake the shared frame loop, without treating it as `BaseGame`. **`SatelliteSyncGame.stop()` fires no callback**, so the controller's Stop wrapper must explicitly call `handlers.onIdle()`, reset local scene/HUD and notify the `useFrameLoop` wake subscriber; one listener and one loop only.
- [ ] **Critical time-unit conversion:** `step: dtSeconds => satellite.update(dtSeconds * 1000)` since its API expects **milliseconds**. Copy live scene into board-local state, project only score/time/level to the common host. Preserve the model's deferred pending-level swap.
- [ ] Use same handle-result helper for `onFail` and `onWin` (both **save once** with `game.getGameData()`); Stop clears to idle with **no fabricated POST**. `cleanup()` stops timer/rAF/gesture handling; late results cannot overwrite new state.
- [ ] Register Satellite with registry/hub expectations **17→18** in the same commit. Jest 16ms→16ms unit check, lock/level-clear/moving target, loss/win/save once, explicit **Stop→idle→no lingering loop**, and stale reward semantics. MCP iOS simulator: lock target → result → Stop/Replay/back; screenshot orbit/beam/finished state.

**Checkpoint:** Satellite uses **exactly the same** frame-loop core as existing BaseGame boards, with correct ms delta and no duplicated timer engine.

## Stage 3 — Extract Ice Slide policy, then native modes (18 → 19)

- [ ] Extract `iceSlideScoreSubmission({score,gameData,reason:'win'|'stop',wasPlaying}) → {score,gameData,context?}|null` into **portable** `@cetus/games/ice-slide`. The numeric `score` is required separately—**`IceSlideGameData` does not contain it**. Return `null` for nonpositive score, Daily early Stop, or already-stopped Stop; preserve Campaign/Expedition score-positive early-stop and winning-run context. **Refactor web `apps/web/src/lib/games/ice-slide/init.ts` to call the same function**; do not copy decision branches into mobile. One Vitest matrix covers web and native consumers, with web Playwright score-context e2e regression.
- [ ] Extract web-only `createExpeditionSeed` into a portable Ice Slide helper; share 4×32-bit hexadecimal format and accept an injectable random-word source so web retains `crypto.getRandomValues` and mobile can use a minimal fallback if Hermes lacks it. Confirm native Hermes behavior in the simulator. No new RNG library or server API.
- [ ] Add `IceSlideBoard.tsx` with Skia cell grid, swipe directional `move`, stage/progress, Undo/Reset Level and a pre-run mode chooser. Use a thin **per-host controller**: `NativeGameChrome`'s zero-argument `actions.start()` (also Play again) starts the **selected mode**, using `game.start()` for Campaign, `createIceSlideDailyRunDefinition(toIceSlideUtcDateKey(new Date()))` for Daily, and `createIceSlideExpeditionRunDefinition(seed)` for Expedition. Cache the Daily and Expedition runs at Start so **Play again reuses the original run**: the same UTC date/runKey (and leaderboard `competitionKey`) even across UTC midnight, matching web `retryRun`, and the same Expedition seed. A distinct board-local **New Expedition** button requests a new seed; a board-local **Stop** invokes the correct score-stop policy. Use safe/risky choices at stages 2 and 4, charge-gated Undo, and no generic Reset button for unavailable actions.
- [ ] Map `onGameStart/onMove/onLevelClear/onTimeUpdate/onWin` into the handle session and use the shared score-policy return value to post **once**. **`IceSlideGame.undo()`, `resetLevel()`, `chooseExpeditionRoute()` and `stop()` emit no callbacks**: controller wrappers must synchronously republish the board scene and stabilized HUD after these actions. A Stop while still playing publishes the local `RUN ENDED` result like web — with `saveStatus` when the policy submits, else a no-save result **without** `saveStatus` for Daily at any score or a zero-score Expedition; `onIdle()` is only for a Stop that shows no result (an already-ended run, or a zero-score Campaign). Daily early Stop never saves; Campaign/Expedition early Stop save only if positive. Preserve exact `gameData`, daily `{mode:'daily',competitionKey:runKey,rulesetVersion}`, Expedition `{mode:'expedition',rulesetVersion}` and unscoped Campaign.
- [ ] **Reuse native leaderboard kit**: `useRemoteData`, `isSingleBoard`, `LeaderboardLoading/Row/EmptyBoard/Error`, `useRefetchOnFocus` from the existing mobile game leaderboard page. New work is only Daily `api.getLeaderboard({gameId:GameID.ICE_SLIDE,mode:'daily',competitionKey:runKey,limit})`, UTC date header and run-keyed query cache; no copied UI error/retry/empty states.
- [ ] Register Ice Slide and update registry/hub expected counts **18→19**. Jest score/stop matrix, UTC date/seed/route determinism, zero-argument Start/Replay mode binding, **same-seed Replay vs New Expedition**, **Daily Replay reusing the original runKey across a simulated UTC-midnight rollover**, **early Daily/Expedition Stop showing a no-save result while a zero-score Campaign Stop shows none**, result cleared on idle, **immediate HUD/cursor refresh after no-callback Undo/Reset/route/Stop**, score/achievement payload, daily scope and retry/error state, late rewards. MCP iOS simulator Campaign, Daily+leaderboard, Expedition route/Undo/replay + active/mode/leaderboard screenshots.

**Checkpoint:** **19/23** native games, and web and mobile now **share** the Ice Slide decision contract.

## Stage 5 — Rhythm Reactor integrated using the proven clock (22 → 23)

- [ ] Integrate the **original HPA-1140** bundled 60-second click track (separate asset PR; do not generate/edit SFX/music here). If HPA-1140 is not ready, **leave this HPA-535 PR open/draft at 22/23; do not split/merge/declare done**. Rebuild the native dev client with `expo-audio` already verified in Stage 0.
- [ ] Add `RhythmReactorBoard.tsx`: Skia four-lane falling notes, labelled tap lanes, readable beat feedback, **pre-run only** bounded millisecond calibration control (default 0, locked while playing) and explicit load/play failure UI. **Start readiness gate:** `BaseGame.start()` synchronously starts a 60s `GameTimer`, while `NativeGameChrome.actions.start()` is synchronous. The Rhythm runtime producer must preload/verify the bundled audio **before enabling the shared Start/Replay UI** (reuse host binding-pending/setup-error behavior or a minimal Start gating seam). On press coordinate player playback readiness with `game.start()`; if audio is not ready or fails to start, the model **must stay idle** and must not post a zero-score run. Confirm start offset in the Stage-0 simulator spike; do not rely only on async audio status changes.
- [ ] **No planned portable Rhythm model change.** Construct `RhythmReactorGame` with `maxUpdateDelta: duration` (web still defaults to 0.1s). Through **the same `useFrameLoop`**, compute `targetSeconds = clamp(player.currentTime - calibrationOffsetSeconds, 0, duration)` only while player is loaded and playing, then `game.update(Math.max(0, targetSeconds - game.getState().elapsedSeconds))`. Render notes from `game.getState().elapsedSeconds`, not a competing wall/media clock; immediately advance to the current audio time **before `hitLane`** for between-frame taps. Positive offset subtracts from player time; lock calibration during play to keep clock monotonic. No `hitLane(atTime)` API or new sync engine.
- [ ] **Explicit non-pausable background policy:** leaving `AppState.active` during a live Rhythm run **aborts** it instead of pretending the model can pause. A Rhythm-specific AppState listener stops/rewinds audio and uses `game.reset()` (no score POST) to return to **idle** and clear notes. Do not auto-resume on foreground; finished/idle runs are untouched. Unsubscribe on runtime disposal; leave the **generic host AppState policy unchanged**. Check the independent **60s wall-clock `GameTimer`** against real audio onset/final playable note; verify clean finish, result and Replay, and revise this same PR if significant drift appears.
- [ ] Jest with fake player and timers: **unloaded/failed audio never invokes `game.start()` or posts**, player-start delay doesn't start a countdown early, first note 2s, 0.5s beats, ±0.08/±0.16 perfect/good, 200ms hitch catch-up, calibration sign, sampling before hit, **background while running → idle/reset/no POST and no auto-resume**, foreground fresh Start, normal 60s finish/one POST, **stale result dropped but same-account late rewards forwarded**, audio player/AppState cleanup.
- [ ] Register Rhythm and update both registry/hub expectations **22→23**. MCP iOS **actual audio playback**, count-in, calibrated lane hit, result/replay/back and screenshots.

**Checkpoint:** **all 23/23** playable. Completion is blocked until the separate audio asset is integrated and native rhythm timing is demonstrated.
