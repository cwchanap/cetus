**Status:** Design-review revision (2026-11-17); documentation only. No runtime implementation or simulator acceptance has been performed in this PR.
**Reviews:** [Initial design review](https://github.com/cwchanap/cetus/pull/110#pullrequestreview-5941818871); [follow-up integration review](https://github.com/cwchanap/cetus/pull/110#pullrequestreview-5942665486).

**Plan:** [Single-PR implementation plan](../plans/2026-11-16-hpa-535-wave3-mobile-plan.md)
**Prerequisite:** [HPA-533 / PR #108](https://github.com/cwchanap/cetus/pull/108) is complete and supplies the native Skia canvas and the first 16 mobile games.
**Related asset-only task:** [HPA-1140](https://linear.app/cwchanap/issue/HPA-1140/create-an-original-60-second-rhythm-reactor-metronome-audio-asset).

## Goal and boundaries

Enable the final seven games in the existing Expo app: **Tetris, Bejeweled, Bubble Shooter, Rhythm Reactor, Circuit Hacker, Satellite Sync and Ice Slide**, preserving their portable `@cetus/games` rules and the web's score/achievement contracts. This brings the sole `NATIVE_GAMES` registry from **16/23 to 23/23** playable games.

There is **one implementation PR for HPA-535**, beginning with these two documentation files. Subsequent coding and testing stages are commits to this same draft PR; do not make seven per-game PRs. Original image art, music or SFX are not coding deliverables. The required original click-track is scoped to HPA-1140 and supplied to this PR later. **Do not merge HPA-535 at 22/23:** the full 23-game acceptance and audio asset remain required in this one PR.

Non-goals: rewrite any game engine, introduce a generic scene/entity graph, add a new scheduler, port PixiJS/web DOM renderers to RN, add a second auth or score transport, change database/API schemas, implement the App Store/Play Store release process, or introduce a new end-to-end testing framework. Authenticated **real web↔app** parity and the Android native/device release gate stay with [HPA-199](https://linear.app/cwchanap/issue/HPA-199/verify-cross-platform-parity-and-release-on-the-app-store-and-google).

## Verified baseline on `main`

- `apps/mobile/src/games/registry.ts` owns the **16 existing** native entries. Each uses `createGame({submitScore,platform})`, `project`/`createProjector`, and a board component. `NativeGameHost.tsx` constructs **one identity-bound** `createScoreSubmitter(settledUserId)`, `createBaseGameSession` + `useGameSession`, forwards structured awards, handles AppState pause for pausable games and disposes on identity change/unmount. `NativeGameChrome.tsx` already handles Start/Replay, HUD, saved/pending/unconfirmed result and rewards. Extend rather than duplicate these.
- `GameCanvas.tsx` already handles Skia letterboxing and `toGamePoint`; `useGameLoop.ts` runs one JS-thread rAF with delta **seconds**, capped at **0.1s**, and updates a board-local scene on lifecycle changes. Existing Skia boards show the host-HUD vs board-scene split. `apps/mobile/__tests__/NativeGameImportGraph.test.ts` guards against DOM/Pixi runtime imports.
- `createHandleSession` already exists in `@cetus/app-core` for callback/imperative games, but **native registry/host currently accept only `BaseGame`**. Circuit Hacker, Satellite Sync and Ice Slide **do not extend `BaseGame`**. Adding them as BaseGame subclasses or faking their model events would duplicate timers and scoring.
- `@cetus/api-client` exposes `getLeaderboard({gameId,mode,competitionKey,limit})`, and `/api/leaderboard` already supports Ice Slide Daily scoped ranking. `@cetus/shared/scores` exposes `ScoreSubmitter` and `ScoreData.context`. No new backend endpoint or database migration is needed.
- Rhythm Reactor's web renderer is currently **visual-only** (no audio asset); the shared model uses a deterministic 60-second, four-lane chart with a **0.5s beat grid**, first note at **2s**, and `update(deltaSeconds)` capped at 0.1s. `apps/mobile/package.json` has Skia and gesture handling but **does not yet include `expo-audio`**. A repository tree scan found no audio file.
- `.github/workflows/ci.yml` has an **always-running draft-PR `mobile-export`** job using `EXPO_PUBLIC_API_BASE_URL=https://cetus-ci.example`, exporting iOS+Android **JS/assets**. Other lint/test/build jobs are draft-gated. Export is **not** a native compilation/device test.
- `useGameLoop` is **BaseGame-specific**: it accesses `isActive/isPaused/isGameOver/getRunId`, subscribes to BaseGame emitter events and calls `update(deltaSeconds)`. Satellite Sync's `update(deltaMs)` and Rhythm's media clock require a small reusable loop core, not separate rAF implementations.
- `apps/web/src/lib/games/ice-slide/init.ts` alone currently decides the per-mode stop/save rules and score context. Mobile cannot import web code; extract those pure rules before the Ice Slide port.
- `apps/mobile/src/lib/leaderboard.tsx` already provides `LeaderboardRow/Loading/Error/EmptyBoard` and `isSingleBoard`; `useRemoteData` lives in `@cetus/app-core`. Do not reimplement this UI state machine.
- Expo SDK 57's `expo-audio` player reports `currentTime` and status. **Playback-status events default to 500ms** (per [Expo SDK 57 docs](https://docs.expo.dev/versions/v57.0.0/sdk/audio/)), too coarse to assume ±80ms gameplay accuracy. An early native playback clock spike must test per-frame sampling and the appropriate update interval.
- HPA-535 has no UI mockup attached, so screenshot-based visual acceptance will use the existing mobile theme, legible safe areas, controls and no canvas clipping as references.

## Architecture decisions

### 1. Keep one native host and two small runtime variants

Keep the existing **16 BaseGame registry entries unchanged** and add four more using that existing production path. The other three games—Circuit Hacker, Satellite Sync and Ice Slide—remain genuine callback/imperative models on `createHandleSession`; no fake BaseGame inheritance or second score client.

**One construction interface, one host.** Both the BaseGame and handle producers return a minimal normalized runtime, conceptually `{ session, binding, view, outcomeLabel?, onRewards, onRunStart, dispose }` (with `outcomeLabel?: (result: GameSessionResult) => string | null`). The producer owns the differences: BaseGame creates its projector, attaches `forwardBaseGameResults` and `'start'` listeners and calls `destroy()`; handle games bind callbacks to `createHandleSession.handlers`, their model-specific controls and `cleanup()`. `NativeGameHost` constructs **one** `createScoreSubmitter(settledUserId)` first, then consumes the normalized runtime without branching at each of its former five BaseGame-only touchpoints. Reuse `useGameSession`, `NativeGameChrome`, AppState capability checks, the existing identity-keyed remount and **one shared reward merge implementation**. Keep variant typing and board bindings local to the producer, not a generic plugin/DI framework. **Preserve the existing `NativeGameEntry.port?: NativeGamePort` shape** (including `port.view` and `port.resultOutcomeLabel(stats)`) for all 16 current entries and their registry/host Jest fixtures; add a separate, explicit `handlePort` variant rather than renaming the old field. The BaseGame producer maps its existing `resultOutcomeLabel(result.stats)` to the normalized `outcomeLabel(result)`. Handle producers provide their own label for solve/failure/stage outcomes. Keep the BaseGame producer's current teardown order **reward forwarder removed → session disposed → game destroyed**, already asserted in `NativeGameHost.test.tsx`; handle cleanup follows equivalent ordering.

**One handle-result helper (needed by all three).** Implement a small helper at the native adapter boundary, reusing existing portable `createRunGuard`, with `beginRun` and a run-specific finish function. `beginRun` resets visible **score/time** and run token. **Fix `createHandleSession` itself**: `handlers.onStart()` and `handlers.onIdle()` must set `result: null` as well as the new status; they currently leave a previous result stored when Replay starts. Update `packages/app-core/src/types.ts` docs: a handle-provided score-eligible finish now reports `pending/saved/unconfirmed`; non-save outcomes still omit `saveStatus`. Preserve previous web islands' display-only behavior and add both `app-core` Vitest and native Jest regression coverage. An eligible finish displays a provisional result (`saveStatus:'pending'`), invokes **one** identity-bound `ScoreSubmitter({gameId,score,gameData,context,platform})`, then updates the same run to `saved` or `unconfirmed`. For no-save outcomes it displays a local result **without claiming a successful or pending save**. Stale completion from a prior run **never overwrites** a newer run's result. However, **same-account late-save achievements/challenges still reach the shared reward banner**, matching the existing BaseGame behavior, because the save legitimately committed before going stale. Only disposed/account-switched runtimes suppress further UI updates. Do not re-POST on failure, duplicate completion, Reset or Replay.

Capabilities are model-truthful: the three handles are `pausable:false` (no generic Pause control). The existing host `AppState` listener already checks `session.capabilities.pausable`; no new background policy is necessary. Boards surface Stop/End/Retry only if those actions exist in the model/web. **The handle `binding` is a stable per-host controller, not an unstructured raw model**: it exposes model-specific start selection and local Stop/Undo/actions plus a synchronous `refresh`/scene projection callback. Because `NativeGameChrome` invokes `actions.start()` with no arguments on both Start and Replay, the controller resolves preselected difficulty/mode and retained seed on that call. Cleanup stops timers/listeners/animations promptly.

**Build this architecture alongside Circuit Hacker**, its first, event-driven consumer; do not make a speculative separate stage with zero registered games.

### 2. Rendering and inputs stay board-local

Reuse `GameCanvas` for all seven Skia boards, the same theme tokens, and existing labelled RN `Button`/`Pressable` controls. GestureDetector/pan/tap logic belongs to the particular board. Use logical coordinates via `toGamePoint` only for pointing/aiming; reject taps in letterbox margins. Avoid 60Hz `NativeGameHost` re-renders: frame-driven boards use a **small stable HUD projector** and a copied primitive-only scene stored locally. Event-/input-driven games use stable projection and model callback invalidation rather than gratuitous frame loops.

**One loop implementation for all time-stepped boards.** Extract the scheduling/timestamp/wake/cancel core from the current BaseGame-only `useGameLoop` into a small board-local `useFrameLoop({ isRunning, step, subscribe, onFrame, lifecycleKey })`. Keep `useGameLoop(game,onFrame)` as the same BaseGame-facing wrapper, so existing 16 boards need no changes. It retains the 0.1-second wall-delta cap, lifecycle scene sync, timestamp reset on pause/idle, and cleanup. Satellite uses `step: dtSeconds => game.update(dtSeconds * 1000)` and a handle-specific lifecycle subscription; Rhythm uses `step: () => advanceToMediaPosition()` and its player-status wake path. No separate rAF engines or cross-platform stepper package.

| Game | Model/input | Rendering/update | Distinct acceptance hazard |
| --- | --- | --- | --- |
| Tetris | `TetrisGame`: swipe left/right/down, tap Rotate, labelled Hold + Hard drop | Skia 10×20 cells, next/hold previews; `useGameLoop` calls existing update; model uses `Date.now()` for gravity | No double movement on a swipe; hold once per piece; top-out produces one result; show **elapsed** time instead of `MAX_SAFE_INTEGER` countdown |
| Bejeweled | `new BejeweledGame(GameID.BEJEWELED, config, callbacks)` (ID required first); `clickCell`: swipe-adjacent → first/second cell, with tap selection fallback | 8×8 Skia jewels; use existing `setAnimator` swap/swap-back/clear hooks with board-local effects; no physics loop | Lock input while `isAnimating`; cascade and reset cancel stale visual work, preserve model-owned score |
| Bubble Shooter | `BubbleShooterGame.setAimAngle` while dragging, `shoot()` once on release | Skia hex board, current/next bubble, aim guide + projectile; existing `update(deltaSeconds)` and model geometry | Use shooter/world logical coordinates and model angle clamp; no accidental shot from letterbox/cancelled gesture or duplicate projectile |
| Rhythm Reactor | `RhythmReactorGame.hitLane`, 4 labelled lane pads + optional tap canvas | Skia notes/lanes; one shared **audio playback clock** for visual note position and judgment | Model/audio time divergence, output/input latency, cleanup after finish/background; no duplicate lane hit |
| Circuit Hacker | Controller owns selected pre-run difficulty and constructs `CircuitHackerGame({difficulty,cellSize}, callbacks)` before Start (no model `setDifficulty` exists); `rotateTile` on tapped cells | Skia grid, locked/powered connectivity | Generation is lazy at Start; rotate locks ignored; solve submits, timeout/manual fail does **not** submit (matching web) |
| Satellite Sync | `SatelliteSyncGame.beginAim/updateAim/endAim` using pan angle | Skia rings/satellites/targets/beams; shared `useFrameLoop` drives `update(deltaSeconds * 1000)` (**milliseconds**) | Do not pass rAF seconds as milliseconds; level clear, beam snap/lock, timer, failure/win and cleanup must remain model-owned |
| Ice Slide | Controller routes zero-argument `actions.start()` to selected mode/retained Expedition run and exposes Stop/New Expedition; `move('N'|'E'|'S'|'W')`, route choice, Undo/reset level | Skia grid/cells; input-driven view projection, no frame loop | Daily UTC key/context, Expedition seed and safe/risky choices, skip Daily early-stop score, proper scoped leaderboard |

The web's Pixi renderers are references for game layout only, **not** native runtime imports. No new art is required for these shapes.

### 3. Rhythm Reactor: one media clock, **explicit GameTimer lifecycle**

**Stage-0 native risk spike:** install SDK-57-compatible `expo-audio` (`expo install`, one root `bun.lock`), rebuild the iOS dev client, and play a **temporary local test file, never committed**. Measure `AudioPlayer.currentTime` sampled from JS frames versus status notifications, initial playback readiness/start offset, background/foreground behavior, 200–500ms hitches, and final audio duration. SDK status notifications default to 500ms: they are not proof of the ±80ms perfect judgment window. Try a shorter player `updateInterval` only if measured behavior requires it. An inaccurate player clock is a blocker to be resolved **in this same PR**, not permission to add a second wall-clock game engine. The real original 60-second click track remains a separate **HPA-1140** asset; no partial 22/23 merge.

**Start must be gated by audio readiness:** `NativeGameChrome` currently calls `actions.start()` synchronously, and `BaseGame.start()` synchronously starts its independent 60s `GameTimer`. Before creating/showing the playable Rhythm session, the native **Rhythm runtime producer** must prepare/verify the bundled `expo-audio` player; keep `bindingPending` (or a minimal equivalent disabled Start state) while loading and use the existing setup-error/retry UI on failure. Player creation, ownership and readiness checks are part of this **one producer**, not a second game host. At Start/Replay, coordinate `player.play()` readiness and `game.start()` so a failed/delayed play **does not begin the model timer**; measure and bound audio-start offset in the Stage-0 spike. The native test must assert that unavailable/failed audio **never calls `game.start()` nor submits a zero-score run**. If the SDK cannot confirm playback quickly, fail the attempt visibly and leave the model idle. Do not assume a playback-status event arrives each frame.

**Background is an explicit no-score abort, not a pause:** Rhythm is model-defined `pausable:false`; the existing host `AppState` listener deliberately does not pause it, while `GameTimer` uses `Date.now()` and keeps aging if JS/audio is suspended. The Rhythm producer installs a **game-specific** `AppState` listener (do not change generic host policy). On leaving `active` **during an active Rhythm run**, immediately stop/rewind the audio and invoke the existing reset/abort pathway (`game.reset()` is resettable and does **not** submit scores), restoring idle and clearing old notes. Never auto-resume. Guard this transition once per run; finished/idle results are not aborted. The `AppState` subscriber and player are disposed with the runtime. Native Jest must cover background → reset/idle/no POST, foreground remaining idle, and a fresh Start after return. This is intentionally stricter than silently allowing a truncated, automatically scored background run.

**No planned portable model API change for judgment:** `RhythmReactorGame` already accepts `maxUpdateDelta` in config (web defaults to 0.1s). Native constructs it with `maxUpdateDelta: duration` and uses the shared `useFrameLoop` to advance **one media-derived model time**:

```ts
const target = Math.max(0, Math.min(duration, player.currentTime - offsetSeconds))
const delta = Math.max(0, target - game.getState().elapsedSeconds)
game.update(delta)
```

Render notes from `game.getState().elapsedSeconds`, and advance to the latest media sample immediately before `hitLane`, so visual notes and judgment share time. Keep the bounded calibration offset **pre-run only** (positive offset subtracts from player time), preventing backwards in-run clock adjustment. On completion/Reset/Replay/Unmount, stop/rewind/release appropriately. **The wall-clock `GameTimer` still owns model completion at 60s**, so the Stage-0/Stage-5 native simulator tests must verify the audio starts in sync and reaches its final playable notes before that deadline; do not claim this purely from Jest or Expo JS export. Any observed timer drift is a concrete design-review issue, not permission to silently accept missing notes or save a 0-score error run.

### 4. Handle games: score boundaries and mode contracts

**Circuit Hacker:** Use a stable controller per host with a **pre-run difficulty selection**. `CircuitHackerGame` takes difficulty **only in its constructor** and has no `setDifficulty()`: the controller stores the selected difficulty, constructs/replaces the model as needed **before `actions.start()`**, cleans up the old instance, and then invokes `startGame()` (which lazily generates its puzzle). Subsequent Replay uses the currently selected difficulty; the model itself remains unchanged. Call `rotateTile` on valid board touches, and map `onGameStart/onTimeUpdate/onRotation/onSolved/onFail` to the handle session. Match web: `onSolved` sends one score with `{difficulty,secondsRemaining,rotationsUsed,solved}`; timeout/manual failure shows honest result without a score POST. Cleanup `game.cleanup()` on host disposal.

**Satellite Sync:** Create once per host, start/stop via `start/stop`, call `beginAim/updateAim/endAim` from a board-local pan converted to world degrees (reuse `geometry.ts` math), and step the moving scene with `update(deltaMilliseconds)`. Forward score/time/level events into the handle session; on **either** `onFail` or `onWin`, submit once with `game.getGameData()` and `platform`. Stop timers and rAF on finish/unmount, handle the pending-level swap at the next update; on Stop return to idle and do not falsely create a score result. **`SatelliteSyncGame.stop()` emits no callback**: the controller's Stop wrapper must explicitly publish `handlers.onIdle()`, reset visible scene/HUD and notify the shared `useFrameLoop` subscription/wake path, preventing stale moving rings or a lingering rAF.

**Ice Slide:** Use the existing pure run factories:
- Campaign: `game.start()` (authored levels).
- Daily: `createIceSlideDailyRunDefinition(toIceSlideUtcDateKey(new Date()))`, frozen once at Start using the **UTC** date, not device-local date.
- Expedition: `createIceSlideExpeditionRunDefinition(seed)`, with same seed retained for Retry, stage-2/4 safe/risky choices and charge-gated Undo. The controller's zero-argument `actions.start()` chooses the board-selected mode and **reuses the materialized Daily or Expedition run** on Replay — a Daily replay after UTC midnight keeps the original date's runKey and leaderboard `competitionKey`, matching web `retryRun`; a separate **New Expedition** action regenerates a seed by explicit choice. Extract the existing web-only `createExpeditionSeed` into `@cetus/games/ice-slide` while retaining the web's secure RNG path and giving native an injected random-word source if Hermes lacks `crypto.getRandomValues`; no new RNG dependency or security subsystem.

**Extract one pure Ice Slide score-decision function into `@cetus/games/ice-slide`, used by BOTH web and native**, before implementing its board. For example:

```ts
iceSlideScoreSubmission({ score, gameData, reason: 'win' | 'stop', wasPlaying })
  // => { score, gameData, context? } | null
```

(The `score` must be an input: `IceSlideGameData` alone does **not** contain the numeric score.) The helper returns `null` for score ≤0, Daily early Stop, or already-ended Stop; for positive scores it chooses canonical daily `{mode:'daily', competitionKey:runKey, rulesetVersion}`, expedition `{mode:'expedition',rulesetVersion}`, or absent Campaign context. Move web `init.ts` onto the helper and give the decision matrix one shared Vitest suite; mobile passes its result to the existing identity-bound submitter. Keep each platform's own transport/toast UI; do not move DOM code into packages or duplicate the stop matrix.

Render stage progress, stars/objectives, mode and summary through Skia plus native controls, without recreating the web DOM initializer. The board/controller owns explicit **Stop** and **New Expedition** controls rather than inventing a global Reset button. `IceSlideGame.undo()`, `resetLevel()`, `chooseExpeditionRoute()` and `stop()` emit **no change callbacks**; after each controller command, synchronously publish a fresh board scene and value-stable HUD projection rather than waiting for a timer tick or frame loop. A Stop while still playing publishes the run's local result like web's `RUN ENDED`: with `saveStatus` when the policy submits, else a no-save result for Daily at any score or a zero-score Expedition; reserve `handlers.onIdle()` for Stops where web shows no result (an already-ended run or a zero-score Campaign). Use existing `useRemoteData`, `isSingleBoard`, `LeaderboardLoading`, `LeaderboardRow`, `EmptyBoard` and `LeaderboardError` from the mobile leaderboard kit; **only** the scoped query `api.getLeaderboard({gameId:GameID.ICE_SLIDE,mode:'daily',competitionKey:runKey,limit})`, date header and run-keyed cache identity are new. Do not copy leaderboard states, introduce endpoints or change the score API.

### 5. Score, lifecycle, accessibility and testing rules

- BaseGame ports retain the existing `submitScore`, `Platform.OS`, structured result and reward path; handle ports use the same injected submitter and platform value. Every expected save is **one POST max**; distinguish pending/saved/unconfirmed and keep guest/identity bindings intact. Prevent stale UI after replay, back navigation or account switch.
- Never leave game timers, rAF, gesture holds, pending animation promises or audio player alive after unmount. Reset/Start/finish must refresh board-local scene even if the model doesn't emit state-change. Don't invent pause support for handle/Rhythm games.
- Accessible labels and clear disabled states for every touch-only control; screen readers must not need to identify Skia primitives to play. Correct hit areas, dynamic phone portrait layout, letterbox touch rejection, readable contrast and safe-area margins.
- Extend `NativeGamesRegistry.test.ts`, `GamesHub.test.tsx` and `NativeGameImportGraph.test.ts` **with each registration commit**, updating 16→17→18→19→20→21→22→23 counts with each registration (Circuit → Satellite → Ice Slide → Tetris → Bejeweled → Bubble Shooter → Rhythm); no speculative registry placeholders.
- Automated Jest/model tests prove model commands, run-mode/context payloads, scene/HUD isolation, time unit conversions, single POST, **stale result dropped but same-account late rewards forwarded**, guest/identity lifetime, stale async callbacks, audio-ready Start gating, non-scoring background abort, handle result cleared on replay/idle, board/controller refresh after callback-free commands, teardown order, and reused daily-scoped leaderboard states.
- **E2E via MCP:** drive the **iOS simulator** for all seven games (hub → Play → Start → game-specific input → visible progression/result → Replay → leave) and capture **active/result screenshots**. Include Rhythm calibration/audio, Circuit solve vs fail, Satellite target lock, Ice Slide Daily leaderboard + Expedition route. With no attached Linear mockup, visually compare screenshots to the existing Cetus mobile chrome/theme and check safe areas, layout, controls, clipping and legibility. Machine-driven screenshot check is required; **human approval is not an acceptance gate**.
- Single-platform iOS simulator acceptance is sufficient for the shared RN UI/game logic; CI still exports **iOS and Android JS**. Native Android compilation/device verification, real OAuth/backend parity and store release remain explicit **HPA-199** gates, not results inferred from iOS/Jest/Metro.

## Completion definition

All seven game ports are **registered and playable** with their web-equivalent mechanics and score metadata; 23/23 catalog entries have a functional Play button. MCP-driven iOS gameplay/visual evidence, mobile Jest/model tests, cross-workspace quality gates and existing web Playwright e2e pass. A Stage-0 iOS audio-clock spike has measured the timing characteristics; the HPA-1140 audio deliverable is integrated and a real simulated iOS playback/calibration flow passes. The one PR **waits for HPA-1140 rather than merging at 22/23**. Any unavailable native build or external authenticated backend proof is **reported as unverified**, never silently marked complete; HPA-199 owns the later cross-platform release checks.
